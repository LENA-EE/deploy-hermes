# Стенд под задачу

Отдельная учётная запись, в которой агент ведёт одну задачу целиком: аудит системы, разбор
legacy, сквозную разработку небольшого сервиса. Внутри — роли-профили, снаружи — та же
песочница, что и у обычных пользователей.

Метка: ⏳ — не разворачивалось.

## Зачем отдельно от личных агентов

| | Личный помощник | Стенд под задачу |
|---|---|---|
| Сколько | по одному на сотрудника | по одному на задачу |
| Для чего | личная работа: разобрать документ, объяснить код, собрать отчёт | одна задача целиком, силами нескольких ролей |
| Рабочая папка | своя, личная | общая для ролей этой задачи |
| Кто направляет | сам сотрудник | один ведущий в каждый момент |
| Срок жизни | пока сотрудник работает | пока идёт задача, потом удаляется |

Причина разделения простая: рабочая копия одна, порт один, файлы общие. Двое одновременно
в одном стенде — конфликты и потерянные правки. Нужна параллельная работа — заводится второй
стенд со своей копией.

Личный агент разработчика при этом не заменяет редактор с ИИ: код пишут там, а к Hermes идут
за разбором незнакомой системы.

## 1. Завести стенд ⏳

```bash
# Учётная запись под задачу. Имя — по задаче, не по человеку.
sudo hermes-user add io2          # аудит ИО2
# sudo hermes-user add dev-abc    # сквозная разработка сервиса ABC
```

Получаем: учётку `hermes-io2` без sudo и без SSH, рабочую папку `/srv/hermes/io2`,
веб-дашборд на своём порту, вход по логину и паролю.

## 2. Роли как профили ⏳

Профиль — это отдельный домашний каталог агента: своя память, свои сессии, свой `SOUL.md`
и свой `config.yaml`. Роли не изолированы друг от друга по файлам (это и нужно — они
обмениваются результатами), но память у каждой своя.

```bash
sudo -iu hermes-io2 hermes-run profile create arch     # археолог: описывает систему как есть
sudo -iu hermes-io2 hermes-run profile create audit    # аудитор: ищет дефекты и риски
sudo -iu hermes-io2 hermes-run profile create dev      # проектировщик/исполнитель
sudo -iu hermes-io2 hermes-run profile create critic   # проверяет выводы остальных
sudo -iu hermes-io2 hermes-run profile list
```

Каждому — свой `SOUL.md` с ролью, ограничениями и форматом результата, и `terminal.cwd`
на рабочую папку стенда. Роль без такого описания — просто ещё один одинаковый чат.

Переключение ролей из браузера появляется после обновления на v0.21.0 (`UPGRADE.md`).
До обновления роли доступны из консоли (`hermes-run -p <роль>`) либо разворачиваются
отдельными экземплярами.

## 3. Раскладка рабочей папки ⏳

```
/srv/hermes/<задача>/
├── repos/<система>/   исходники: копия, ТОЛЬКО ЧТЕНИЕ
├── notes/             результаты ролей: отчёты, находки, предложения
└── work/              черновики, сборки, временные файлы
```

```bash
sudo install -d -m 755 /srv/hermes/io2/repos
sudo install -d -m 700 -o hermes-io2 -g hermes-io2 /srv/hermes/io2/notes /srv/hermes/io2/work

# Репозиторий — копия, без адресов удалённых репозиториев и без ключей.
sudo git -C /srv/hermes/io2/repos/<система> remote remove origin 2>/dev/null
sudo find /srv/hermes/io2/repos \( -name '.netrc' -o -name 'id_rsa*' -o -name '*.pem' \
     -o -name '.npmrc' -o -name '.pypirc' \) -print -delete

# Владелец root, пользователю только чтение: агент читает, изменить не может.
sudo chown -R root:root /srv/hermes/io2/repos
sudo chmod -R a-w,a+rX /srv/hermes/io2/repos
```

`.git` оставляем — история отвечает на вопрос «почему код такой», и по ней Hermes определяет
корень репозитория. Но **до переноса** нужно подтверждение владельца, что в истории нет паролей
и ключей, когда-либо закоммиченных и позже удалённых: агент их прочитает, и они уйдут в модель.

## 4. Что стенду разрешено ⏳

Наследуется от обычного пользователя, ничего дополнительно не открывается:

- без sudo, без доступа к чужим каталогам, `/opt` только на чтение;
- опасные команды — только после подтверждения человеком (`approvals.mode: manual`);
- фоновым задачам опасные команды запрещены (`cron_mode: deny`);
- пакеты сам не доустанавливает (`allow_lazy_installs: false`);
- интернета нет; из сети доступен только сервис модели.

Для сквозной разработки этого достаточно: сервис поднимается на локальном порту выше 1024
от имени самой учётной записи, агент обращается к нему запросами, читает журнал, правит код,
перезапускает. Всё внутри контейнера — новых сетевых проходов не требуется.

Чего **нет** и что потребует отдельного согласования: браузер внутри контейнера (визуальная
проверка страниц), доступ к Jira и Bitbucket, право записи в репозитории.

## 5. Ресурсы ⏳

По умолчанию на экземпляр: 1.5 ГБ памяти, 150% CPU, 256 процессов; на всех вместе — 5 ГБ и 300%
(`hermes.slice`). Для стенда со сборками и запуском сервисов этого может не хватать: лимиты
поднимаются в юните для конкретного экземпляра, а не для всех сразу.

```bash
sudo systemctl show hermes-dashboard@io2 -p MemoryMax -p CPUQuota -p TasksMax   # что сейчас
sudo systemd-cgtop -1 /hermes.slice                                             # кто сколько ест
```

## 6. Порядок работы ⏳

1. Ведущий ставит задачу роли `arch` — та описывает систему в `notes/01-architecture.md`.
2. `audit` работает поверх карты, находки — в `notes/02-findings.md`, каждая с файлом и строкой.
3. `critic` проверяет находки, пытаясь их опровергнуть, — `notes/03-critique.md`.
4. `dev` проектирует решение по проверенному — `notes/04-proposal.md`.
5. Человек переносит принятое в рабочий репозиторий обычным порядком, через ревью.

Обмен между ролями — через файлы, а не через разговор: каждый вывод зафиксирован, видно, кто что
утверждал, и результат переживает перезапуски.

**Граница, которая не двигается:** ни одна строка не попадает в рабочий репозиторий иначе,
чем через человека и обычное ревью. Агент не вливает изменения, не деплоит и не закрывает задачи
от чьего-либо имени.

## 7. Закрытие стенда ⏳

Стенд временный. По окончании задачи:

```bash
sudo hermes-user list             # что заведено
sudo hermes-user purge io2        # учётка, копия репозитория и вся переписка удаляются
```

Перед удалением — забрать из `notes/` то, что нужно сохранить, и положить туда, где команда
хранит документы. Бессрочно лежащие копии банковских систем в контейнере — лишний разговор с ИБ.

## Согласования

- Копию репозитория в контейнер — с владельцем системы и с ИБ: содержимое файлов уходит
  в сервис модели, это механизм работы агента.
- Любые дополнительные компоненты (браузер, библиотеки для офисных форматов) — внесение
  стороннего ПО: согласование и антивирусная проверка, с перечнем файлов и SHA-256.
- Доступ к Jira, Bitbucket и право записи — отдельный этап, отдельные заявки.
