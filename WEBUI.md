# Hermes WebUI в контейнере

Пакет: `webui/hermes-webui-0.51.69-offline.zip` — WebUI v0.51.69 (15.05.2026) под Hermes v0.13.0,
все CDN-библиотеки внутри, интернет не нужен. Что изменено против оригинала — `OFFLINE-PATCH.md` в архиве.
SHA-256: `b9a544b4b76dfec790f6616f2fe870df01e6093380aa03bcea6ed5c99965121c`

Метка: ⛔ — **отложено, в контейнере не запускалось.** Решение от 28.09.2026: не вносим, пока
не станет ясно, чего не хватает в штатном дашборде после обновления. Основание и оговорки ниже.

## Почему отложено

Сторонний интерфейс предлагался ради работы с файлами. В штатном дашборде v0.21.0 это уже есть:
страница **Files** (просмотр, правка, загрузка, скачивание) и вставка изображений в чат
(`/api/chat/image-upload`, до 25 МБ). Вносить стороннее ПО ради того, что есть у вендора,
смысла нет: у штатного и поддержка производителя, и корпоративный вход, и журнал входов.

Что проверено по исходникам и что важно знать, если к нему всё же вернёмся:

| Факт | Следствие для контура |
|---|---|
| Оригинальная версия при **каждой загрузке страницы** тянет `xterm` и `prismjs` с `cdn.jsdelivr.net` | В закрытом контуре терминал и подсветка кода не работают. Наш архив 0.51.69 пропатчен (библиотеки внутри) — **любую новую версию придётся патчить так же** |
| Установщик тянет `install.sh` с GitHub и пакеты с PyPI | Ставить только из офлайн-архива, сетевой установщик не использовать |
| За обратным прокси обязательны `HERMES_WEBUI_TRUST_FORWARDED_HOST=1`, при нестандартном порте — `HERMES_WEBUI_ALLOWED_ORIGINS` | Без них встроенная защита от подделки запросов режет обращения из браузера |
| Вход: пароль `HERMES_WEBUI_PASSWORD`, passkeys, свой OIDC; cookie `SameSite=Lax`, срок 30 дней | Модель однопользовательская: один экземпляр на сотрудника, как у дашбордов |
| Стриминг через SSE, не websockets | В nginx нужен `proxy_buffering off` и длинный таймаут; заголовки `Upgrade` не нужны |
| Сервер — `ThreadingHTTPServer` из стандартной библиотеки, агент запускается внутри процесса | Наследует изоляцию учётной записи ОС, как и дашборд |
| Делегирование подагентам реализовано (карточки в панели инструментов, возврат результата) | Для разбора больших задач годится |
| Проект сторонний, один сопровождающий | Внесение — полная процедура: согласование ИБ и антивирусная проверка |

Шаги ниже сохранены на случай, если решение изменится.

## 1. Занести и распаковать ⏳

WinSCP: `hermes-webui-0.51.69-offline.zip` и `deploy/hermes-webui@.service` → в свой хомяк.

```bash
sha256sum ~/hermes-webui-0.51.69-offline.zip           # сверить с хешем выше — файл дошёл целым
sudo /opt/hermes/hermes-agent/venv/bin/python -m zipfile -e ~/hermes-webui-0.51.69-offline.zip /opt/   # распаковать (unzip может не быть)
sudo mv /opt/hermes-webui-0.51.69 /opt/hermes-webui
sudo chown -R root:root /opt/hermes-webui && sudo chmod -R go-w,a+rX /opt/hermes-webui   # код только на чтение
```

## 2. Юнит ⏳

```bash
sudo install -m 644 ~/hermes-webui@.service /etc/systemd/system/
sudo install -d -m 755 /etc/hermes/users
printf 'PORT=9121\nENABLED=yes\n' | sudo tee /etc/hermes/users/agent.conf >/dev/null   # порт для hermes-agent
sudo systemctl daemon-reload
sudo systemctl start hermes-webui@agent
sudo systemctl status hermes-webui@agent --no-pager | head -15
sudo journalctl -u hermes-webui@agent -n 40 --no-pager                                 # если не active — причина здесь
sudo ss -tlnp | grep 9121                                                               # ждём 127.0.0.1:9121
```

> ⚠️ **Доступ к веб-интерфейсу — только через согласованный канал** (публикация сервиса
> администраторами с авторизацией пользователей). Работоспособность проверяется из консоли контейнера:
> `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<порт>` → `200`.
