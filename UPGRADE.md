| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Штатный веб-интерфейс, обновлённый до v0.21.0** | ✅ **делаем.** Закрывает файлы, роли и вход; ничего не нужно ставить сотрудникам; поддержка производителя; новых согласований, кроме внесения дистрибутива, не требует    |

Роли для аудита (архитектор, аудитор, проектировщик, критик) делаются **профилями** внутри
учётной записи сотрудника и переключаются в боковой панели. Это и есть «боты» — то же самое,
только без картинок и без совместного чата.

Разделы 0–6 — то, что делаем. Раздел 7 — справочный, к нему возвращаемся только если после
обновления выяснится, что чего-то критично не хватает.

## Зачем обновляемся

| Что даёт                                                                                                                            | Что меняется у нас                                                                                                                   |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Исправлен запуск чата с готовой сборкой (issue #56665): сначала ищется готовый `entry.js`, npm вызывается только при его отсутствии | Не нужны `ui-tui/node_modules` (8 МБ) и подкладка `hermes-ink` под двумя именами — вносим меньше файлов                              |
| Переключение профилей в веб-интерфейсе (`ProfileSwitcher`, `ProfileProvider`)                                                       | Роли для аудита можно держать профилями одного пользователя, а не отдельными экземплярами                                            |
| Модуль `dashboard_auth` с провайдером `self_hosted` (OpenID Connect)                                                                | Возможен вход по доменным учётным записям вместо `htpasswd` — пароли перестают быть нашей заботой                                    |
| Навык `subagent-driven-development`                                                                                                 | Разбор большой кодовой базы ролями без отдельных процессов                                                                           |
| Страница **Files**: просмотр, правка, загрузка и скачивание файлов рабочей папки прямо в браузере                                   | Снимает главное ограничение текущей версии — материалы больше не нужно копировать текстом, а результаты выгружать вручную через SFTP |
| Вставка и перетаскивание изображений в чат (`/api/chat/image-upload`)                                                               | Скриншоты можно отдавать агенту напрямую                                                                                             |

Чего обновление **не** даёт: раздельной памяти внутри одного экземпляра — изоляция
по-прежнему держится на учётных записях ОС. Совместного чата нескольких агентов в вебе тоже
нет: он существует только в настольном приложении (см. раздел 7).

### Запрет флага `--insecure` ⚠️

Новая версия включает собственную авторизацию автоматически, но только «при привязке
к не-loopback адресу **без `--insecure`**». То есть один флаг снимает защиту полностью.

**Флаг `--insecure` не применяется ни при каких обстоятельствах.** Проверять его отсутствие
в юнитах после каждой правки и после любых работ, выполненных не нами:

```bash
sudo grep -r 'insecure' /etc/systemd/system/hermes-*.service && echo 'НАЙДЕН — убрать' || echo 'чисто'
```

## 2–5. Установка, переключение, откат ⏳

Команды — **только в `CHECKLIST.md`**, чтобы два документа не расходились. Здесь — почему схема такая.

Состояние контейнера, проверенное 06.10.2026:

- `/opt/hermes -> /opt/hermes-2026.5.7` — символическая ссылка;
- `/etc/hermes/hermes.env`: `HERMES_PYTHON=/opt/hermes/hermes-agent/venv/bin/python`,
  node, rg, ffmpeg и браузеры — в `/opt/hermes/tools` и `/opt/hermes/ms-playwright`;
- окружение старой версии построено на `/opt/hermes-2026.5.7/tools/python/bin/python3.11`;
- node v24.15.0 (новой версии нужен 22.22+, 24.11+ или 26+ — подходит);
- работают только дашборды `hermes-dashboard@*`, шлюзов и webui нет.

Решения:

1. **Обёртка `hermes-run` не меняется.** Она универсальная: Python берёт из `hermes.env`.
   Прежний план заменить её на вариант с `cd /opt/hermes` отклонён: агент оказывался бы в каталоге
   программы вместо своей рабочей папки, терялись `PATH` к node и `unset LD_LIBRARY_PATH`,
   а откат не возвращал старую обёртку — после него не стартовал бы ни один дашборд.
2. **Окружение новой версии — в `hermes-agent/venv`, как у старой.** Строка `HERMES_PYTHON`
   подходит обеим версиям.
3. **Код находится через `hermes-code.pth`** в `site-packages` окружения, а не через текущий
   каталог. Агент работает в `/srv/hermes/<имя>`, шлюз запускается через ту же обёртку.
4. **В комплекте нет node, rg, ffmpeg, Python и браузеров** (`tools/` в новой версии — Python-код
   Hermes). Поэтому `hermes.env` до переключения переводится на абсолютные пути
   `/opt/hermes-2026.5.7/...`: для работающей версии это те же файлы. Следствие: **старый каталог
   удалять нельзя**, пока не внесены собственные node и Python.
5. **Переключение и откат — одна ссылка `/opt/hermes`.** Перед переключением — копия
   `/home/hermes-*/.hermes`: новая версия может перестроить базу, и старая на ней не стартует.
6. **Экземпляры поднимаются по сохранённому списку**, а не по шаблону `hermes-dashboard@*`:
   шаблон в `systemctl start` срабатывает только на загруженные юниты.

Схему `config.yaml` (раздел `dashboard.*` и др.) проверяем по факту на тестовой учётке
`probnik`: `hermes-run logs errors` после первого запуска покажет непонятые ключи. Если ключи
изменились — правим `/etc/hermes/config.template.yaml`, а конфиги уже заведённых пользователей
пересобираем вручную (`hermes-user regen` их не трогает, см. `INSTALL.md`, 7.1).

### 7.0. Сторонний веб-интерфейс: решение

Вариант с `nesquena/hermes-webui` рассматривался как способ получить работу с файлами и отклонён
28.09.2026: то же самое есть в штатном дашборде v0.21.0, а сторонний проект дополнительно
обращается к внешним библиотекам в интернете при каждой загрузке страницы. Подробности
и оговорки — в `WEBUI.md`.

### 7.1. Что это даёт

| Возможность                                  | В браузере                         | В настольном приложении                     |
| -------------------------------------------- | ---------------------------------- | ------------------------------------------- |
| Прикрепление произвольных файлов к сообщению | нет (файлы — через страницу Files) | есть, перетаскиванием в чат                 |
| Изображения в чат                            | есть, вставкой и перетаскиванием   | есть                                        |
| Роли (профили)                               | переключатель в боковой панели     | они же в виде ботов                         |
| Совместное обсуждение ролями                 | нет                                | групповой чат, до 6 участников, до 3 кругов |

### 7.2. Принцип: приложение — только окно

Приложение умеет работать в удалённом режиме: агент **не** запускается на рабочей станции,
а приложение подключается к серверной части в контейнере (Settings → Gateways: адрес и учётные
данные).

> ⚠️ **Требования к рабочей станции в этом режиме по документации не определены.** Описанный
> в документации запуск (`hermes desktop`) ставит зависимости Node, собирает приложение Electron
> (~114 МБ загрузки) и требует установленного Hermes с Python. Про готовый установочный пакет
> сказано, что он есть, но не сказано, нужны ли для него Node и Python. Выяснить до того, как
> обещать коллегам «ничего ставить не надо, кроме самой программы».

> Документация к разделу Gateways предлагает в том числе подключение через SSH-туннели.
> Этот способ у нас не применяется: доступ — только через согласованную администраторами
> публикацию сервиса.

Отсюда главное: **песочница сохраняется полностью.** Агент остаётся в контейнере под учётной
записью без sudo, с теми же ограничениями systemd и лимитами. На станции нет ни агента, ни
его прав, ни его данных. Групповой чат ботов тоже исполняется на сервере: все участники —
профили одного пользователя, живут на одном шлюзе.

```
рабочая станция: настольное приложение (только отображение)
        │  https, вход по учётным данным
        ▼
корпоративный прокси → nginx в контейнере → по имени вошедшего в его порт
        ▼
hermes-gateway@ivanov   127.0.0.1:9231   ─┐  обе службы — под учёткой
hermes-dashboard@ivanov 127.0.0.1:9122   ─┘  hermes-ivanov, в своей песочнице
        └── профили (боты): arch, audit, go, critic — память в /home/hermes-ivanov
```

### 7.3. Состав работ

1. **Обновление до v0.21.0** — без него нет ни ботов, ни встроенной авторизации (шаги 0–5).
2. **Шаблон юнита `hermes-gateway@.service`** — копия `hermes-dashboard@.service` с тем же
   блоком ограничений; команда поднимает серверную часть на `127.0.0.1:<порт>`.
3. **Раскладка портов:** дашборды 9122–9199, шлюзы 9231–9299 — чтобы не пересекались.
4. **Правила nftables на новые порты** — тот же принцип: к порту шлюза подключаются только
   владелец, nginx и root. Дописывается в генератор правил внутри `hermes-user`.
5. **Авторизация.** Приложение не понимает проверку пароля средствами nginx — ему нужна
   встроенная авторизация Hermes (логин/пароль или OpenID Connect). Для шлюза включаем её,
   nginx оставляем только проксировать. Целевой вариант — OpenID Connect с корпоративными
   учётными записями: тогда пароли не раздаются вручную и меняются сотрудником самостоятельно.
6. **Публикация второго сервиса** — отдельная заявка администраторам, по аналогии с уже
   открытым веб-интерфейсом.
7. **Доработка `hermes-user`** — выдавать два порта, поднимать две службы, дописывать правила
   на оба порта, прописывать параметры авторизации.

### 7.4. Что требуется от администраторов и ИБ

- Внести настольное приложение в перечень разрешённого ПО и установить сотрудникам штатным
  порядком (внесение стороннего ПО — только после согласования и антивирусной проверки).
- Опубликовать второй сервис контейнера с авторизацией.
- Подключить корпоративный вход: адрес провайдера (`issuer`) и идентификатор приложения.

Первые два пункта самые долгие — начинать с них, лучше одной заявкой.

### 7.5. Проверить после обновления, до раздачи приложения

- Точная команда запуска серверной части и её параметры.
- Ключи конфигурации, отвечающие за авторизацию шлюза.
- Что шлюз видит только профили своего пользователя и не показывает чужие.
- Страницы **Channels** и **Webhooks** в дашборде позволяют подключать внешние площадки
  обмена сообщениями — решить с ИБ, отключаем или разрешаем, до того как пускать людей.
- Отсутствие `--insecure` в юнитах (см. выше) — проверять после каждого обновления.
- Страница **Files**: ограничение каталога на уровне приложения **неполное** — запросы `/api/fs/*`
  его не проверяют (подтверждено тестированием сборки). Настоящая граница — права ОС: под обычным
  пользователем все попытки выйти за свои пределы дают отказ. Обязательно:
  `Environment=HERMES_DASHBOARD_FILES_ROOT=/srv/hermes/%i` в юните как второй рубеж,
  и ни при каких условиях не запускать экземпляр от имени root.
- Замер памяти: экземпляр в покое занимает около 140 МБ, а не 55 — пересчитать план по числу
  пользователей (см. «Масштабирование» в `RUN.md`).
- Часовой пояс: прописывается **в каждом профиле отдельно**, иначе роли считают время по UTC.
  Журналы пишутся по системным часам контейнера.
